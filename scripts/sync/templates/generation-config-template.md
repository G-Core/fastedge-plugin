# Generation Config — <REPO_NAME>

> **What this file is**: Structured instructions for generating `docs/` from source code.
> **How to use it**: Run `./fastedge-plugin-source/generate-docs.sh` which reads this file and invokes Claude per doc file.
> **Who reads this**: The generation script + Claude CLI. The plugin pipeline does NOT read this file.
>
> **Setup**: Copy this file and `generate-docs-template.sh` to `<your-repo>/fastedge-plugin-source/`.
> Rename `generate-docs-template.sh` → `generate-docs.sh`. Customize all sections below.
> Delete these blockquotes when done.
>
> **Reference implementation**: `fastedge-test/fastedge-plugin-source/` — proven end-to-end with the plugin pipeline.

## Global Rules

> These rules apply to ALL doc files generated by the script. They are injected into every
> prompt automatically. Customize the Audience section; the rest is proven and should be kept as-is.

### Audience

> **CUSTOMIZE THIS**: Replace <PACKAGE_NAME> and describe your actual consumers.

These docs are for **consumers** of `<PACKAGE_NAME>` — developers using this package in their projects. They are NOT for contributors developing this repo.

This distinction drives what to include and exclude:
- **Include**: anything a consumer needs to use the package (public API, config options, exported types)
- **Exclude**: internal implementation details, contributor workflows, build system details
- **Test**: "Would someone installing this package need to know this?" If no, leave it out.

### Style
- Technical prose only — no marketing language, no superlatives, no "easily" or "simply"
- Use code signatures for all parameters and return types (TypeScript, Rust, etc.)
- Use fenced code blocks for all examples (language-tagged)
- Use tables for structured data (endpoints, config fields, message types)
- Tables must use padded columns aligned to the widest cell in each column. Pad every cell with spaces so columns line up visually in raw markdown. The separator row dashes must match each column's padded width.
  Good: `| Variable             | Type     | Default |`
  Bad:  `| Variable | Type | Default |`
  Good: `| -------------------- | -------- | ------- |`
  Bad:  `|---|---|---|`
- Every code example must be self-contained and runnable

### Structure
- Every doc file starts with a level-1 heading and a one-line description
- Use level-2 headings for major sections, level-3 for subsections
- No table of contents — keep files navigable by heading structure alone
- End each file with a "See Also" section linking to related doc files

### Exclusions (apply to all files)
- No internal implementation details (how the code works internally)
- No source code file paths or line numbers
- No version history or changelog entries
- No references to `context/` or `CLAUDE.md` (those are internal developer docs)

### Accuracy
- Never hardcode version numbers, Node requirements, or other values that exist in source files (e.g. `package.json` `engines.node`). Instead, instruct the generator to read them from the source. Hardcoded values drift silently.
- All type signatures in docs must match the actual source code declarations

### Coverage Rule
- Every public export, endpoint, type, config option, and env var must appear in exactly one doc file
- If something is referenced in multiple files, one file is authoritative (has the full definition) and others link to it

> ## Per-File Sections
>
> Add one `## docs/<filename>.md` section per doc file. Each section must include:
>
> ### Required subsections:
>
> **### Source Files** — list which source files the agent should read for this doc.
> Be specific (file paths, what to look for in each). The `generate-docs.sh` script
> also needs these in its `SOURCE_FILES` associative array.
>
> **### Scope** — what this file covers and what it does NOT cover (with links to
> the correct file). Explicit scope boundaries prevent duplication across docs.
>
> **### Required Content** — enumerate everything that MUST be documented.
> Be exhaustive. If the agent can skip it, it will.
>
> **### Structure** — a heading outline in a fenced code block showing the exact
> section structure the generated file should follow.
>
> ### Optional subsections:
>
> **Type accuracy notes** — when LLMs commonly hallucinate types (e.g. arrays vs
> records, nullable vs optional), add a CRITICAL section with exact shapes copied
> from source. This is the single most effective way to prevent type errors.
>
> **DO NOT document lists** — explicitly list internal/private APIs that must be
> excluded. LLMs tend to document everything they find in source code.
>
> ### Example (adapt to your repo):

## docs/API.md

### Source Files
- `src/server.ts` (route handlers)
- `src/types.ts` (request/response types)

### Scope
Complete API reference. Every public endpoint.

**This file does NOT cover**: WebSocket protocol (→ WEBSOCKET.md), configuration (→ CONFIG.md).

### Required Content
For every endpoint, document:
- HTTP method and path
- Request/response types with TypeScript signatures
- Example request/response
- Error responses

**Endpoints that MUST be documented**:
1. `GET /health` — health check
2. `POST /api/action` — main action endpoint

**Internal endpoints — DO NOT document**:
- `GET /api/internal` — used by VSCode extension only

### Structure
```
# API Reference
## Base URL
## Endpoints
### GET /health
### POST /api/action
## Error Handling
## See Also
```

> Repeat `## docs/<filename>.md` sections for each doc file your repo generates.
> See `fastedge-test/fastedge-plugin-source/.generation-config.md` for a complete
> real-world example with 8 doc files.
