# Release Pipeline Plan — Decoupled Sync and Release

**Status:** Draft — awaiting approval
**Created:** 2026-04-14
**Author:** Gordon + Claude

---

## Problem

The `sync-reference-docs` workflow regenerates `docs-index.json` in every per-repo sync PR. When two source repos (e.g., `fastedge-sdk-js` and `fastedge-test`) both sync, their PRs each contain a full regeneration of `docs-index.json` — including a `generated_at` timestamp and `source.commit` that differ between runs. Merging one PR makes the other conflict on `docs-index.json`, even though the reference `.md` files they touch are completely disjoint.

## Solution

Decouple the pipeline into two concerns:

1. **Sync pipeline** — handles reference content only (`.md` files). No index, no version bump, no release.
2. **Release pipeline** — scheduled cron (weekly, Tuesday 06:00 UTC) + manual dispatch. Regenerates `docs-index.json`, bumps plugin version, tags a GitHub release, notifies the MCP server.

This eliminates the merge conflict, batches multiple sync PRs into a single release, and establishes the versioned release model needed for future marketplace auto-updates (Claude Code and Codex).

## Design Decisions

| Decision                   | Choice                                      | Rationale                                                                                                                         |
| -------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Index regeneration trigger | Cron (weekly, Tue 06:00 UTC) + `workflow_dispatch` | Batches a week's syncs into one release; avoids multiple regenerations from multiple merges. Manual override covers urgent updates. |
| Index commit target        | Direct commit to `main`                     | Index is deterministically derived from files already on `main`. No human judgment needed — a PR would be ceremony without value. |
| Plugin version bump        | Automated in release workflow               | Semantic: patch bump for reference-only changes. Minor/major reserved for skill or feature changes (manual).                      |
| MCP server deployment      | Automated via `repository_dispatch`         | MCP server auto-syncs docs, bumps version to match plugin release, commits, tags, and builds Docker image. All three consumers (Claude, Codex, MCP) release in lockstep. |
| User update mechanism      | Manual (`git pull` / `docker pull`) for now | B3 (marketplace auto-update) is the end goal. This plan builds the release infrastructure B3 will hook into.                      |
| Staleness window           | Up to ~1 week for reference docs            | Acceptable. Reference docs are informational, not breaking changes. Users already have pull-lag on top of this.                   |

## Current State

- Triggers: `repository_dispatch` (type: `fastedge-ref-update`) and `workflow_dispatch`
- Calls `process-repos.sh` which fetches source, generates `.md` via Claude, reviews via OpenAI

### Task 2: Untrack docs-index.json and add to .gitignore

**Repo:** `fastedge-plugin`

**Context:** With Task 1, `docs-index.json` won't be staged in sync PRs. However, if a developer runs `generate-docs-index.sh` locally or if the file is modified by another process, we don't want it accidentally included in a sync PR.

**Important:** `.gitignore` only affects **untracked** files. Since `docs-index.json` is already tracked by git, adding it to `.gitignore` alone has no effect — modifications will still appear in `git diff` and `git status`. The file must first be removed from the index with `git rm --cached`.

**Changes:**
1. Add `plugins/gcore-fastedge/docs-index.json` to `.gitignore`
2. Run `git rm --cached plugins/gcore-fastedge/docs-index.json` to untrack it (the file remains on disk but is removed from the git index). This will appear as a deletion in the transition commit.
3. The release workflow uses `git add --force` to re-add it at release time, bypassing `.gitignore`.

After the transition commit, `.gitignore` takes effect: local regeneration won't show in `git status`, and sync PRs can't accidentally include it.

**Test criteria:**

- [ ] After `git rm --cached`, `git status` shows the file as deleted (expected in transition commit)
- [ ] After committing the deletion + `.gitignore`, running `generate-docs-index.sh` locally does not cause `git diff` to show changes
- [ ] Release workflow (Task 3) can still commit the file via `git add --force`

### Task 3: Create release workflow

**Repo:** `fastedge-plugin`
**New file:** `.github/workflows/release-plugin.yml`

**Triggers:**

```yaml
on:
  schedule:
    - cron: "0 6 * * 2" # Every Tuesday at 06:00 UTC
  workflow_dispatch:
    inputs:
      bump_type:
        description: "Version bump type (patch for reference-only, minor/major for features)"
        type: choice
        required: false
        default: "patch"
        options: [patch, minor, major]
      force:
        description: "Run even if no reference changes detected"
        type: boolean
        required: false
        default: false
```

**Concurrency:**

```yaml
concurrency:
  group: release-plugin
  cancel-in-progress: false
```

**Steps:**

1. **Checkout `main`**

2. **Detect changes since last release:**

   ```bash
   LAST_TAG=$(git describe --tags --abbrev=0 --match 'v*' 2>/dev/null || echo "")
   if [ -n "$LAST_TAG" ]; then
     CHANGED=$(git diff --name-only "$LAST_TAG"..HEAD -- \
       'plugins/gcore-fastedge/skills/*/reference/**/*.md')
   else
     CHANGED="first-release"  # No prior tag — always release
   fi
   ```

   Exit early if `CHANGED` is empty and `force` is not set.

3. **Regenerate `docs-index.json`:**

   ```bash
   bash scripts/sync/generate-docs-index.sh
   ```

4. **Bump version in both plugin manifests:**
   - `plugins/gcore-fastedge/.claude-plugin/plugin.json`
   - `plugins/gcore-fastedge-codex/.codex-plugin/plugin.json`

   Use a small inline script or `jq` to increment the patch version (or minor/major based on `bump_type` input). Both plugins bump in lockstep.

5. **Commit to `main`:**

   ```bash
   git add --force plugins/gcore-fastedge/docs-index.json
   git add plugins/gcore-fastedge/.claude-plugin/plugin.json
   git add plugins/gcore-fastedge-codex/.codex-plugin/plugin.json
   git commit -m "release: v${NEW_VERSION} — update docs index and bump version"
   git push origin main
   ```

6. **Tag and create GitHub Release:**

   ```bash
   git tag -a "v${NEW_VERSION}" -m "Release v${NEW_VERSION}"
   git push origin "v${NEW_VERSION}"
   gh release create "v${NEW_VERSION}" --title "v${NEW_VERSION}" --generate-notes
   ```

7. **Notify MCP server:**
   ```yaml
   - uses: peter-evans/repository-dispatch@v3
     with:
       token: ${{ secrets.CROSS_REPO_TOKEN }}
       repository: G-Core/FastEdge-mcp-server
       event-type: plugin-release
       client-payload: >-
         {
           "version": "${{ env.NEW_VERSION }}",
           "tag": "v${{ env.NEW_VERSION }}",
           "commit": "${{ github.sha }}"
         }
   ```

**Permissions:**

```yaml
permissions:
  contents: write # commit + tag + push to main
  pull-requests: write # not needed but harmless
```

**Notes:**

- The `CROSS_REPO_TOKEN` secret must have `repo` scope on `G-Core/FastEdge-mcp-server`. Check if the existing FastEdge[bot] GitHub App provides this — if so, use an app installation token instead of a PAT.
- Cron schedule `0 6 * * 2` runs every Tuesday at 06:00 UTC. GitHub Actions cron can delay by up to ~60 minutes; at weekly intervals this is negligible.
- The version bump script must handle both `0.1.0` → `0.1.1` (Claude) and `1.0.0` → `1.0.1` (Codex) patterns.

**Test criteria:**

- [ ] Manual dispatch with `force: true` succeeds on a branch with no reference changes (tests the full flow)
- [ ] Manual dispatch without `force` exits early when no `.md` files changed since last tag
- [ ] `docs-index.json` is correctly regenerated and matches current `.md` files on `main`
- [ ] Both `plugin.json` files have their version bumped
- [ ] Git tag `v{VERSION}` is created and pushed
- [ ] GitHub Release is created with auto-generated notes
- [ ] `repository_dispatch` is sent to `FastEdge-mcp-server` (verify via workflow run in that repo)
- [ ] Running twice with no changes between runs produces no new release (idempotent)

### Task 4: Create MCP server auto-release workflow

**Repo:** `FastEdge-mcp-server`
**New file:** `.github/workflows/sync-and-release.yml`

**Triggers:**

```yaml
on:
  repository_dispatch:
    types: [plugin-release]
  workflow_dispatch:
    inputs:
      plugin_ref:
        description: "fastedge-plugin ref to sync from (tag or branch)"
        type: string
        required: false
        default: "main"
```

**Concurrency:**

```yaml
concurrency:
  group: sync-and-release
  cancel-in-progress: false
```

**Steps:**

1. **Checkout `FastEdge-mcp-server`**

2. **Sparse checkout `fastedge-plugin`** at the released tag (from dispatch payload) or `main` (manual):

   ```bash
   REF="${{ github.event.client_payload.tag || inputs.plugin_ref || 'main' }}"
   PLUGIN_VERSION="${{ github.event.client_payload.version || '' }}"
   git clone --depth 1 --sparse --branch "$REF" \
     https://github.com/G-Core/fastedge-plugin.git /tmp/fastedge-plugin
   cd /tmp/fastedge-plugin
   git sparse-checkout set \
     plugins/gcore-fastedge/skills/fastedge-docs/reference \
     plugins/gcore-fastedge/skills/test/reference \
     plugins/gcore-fastedge/docs-index.json
   ```

3. **Run sync script** (modified — see Task 5):

   ```bash
   PLUGIN_PATH=/tmp/fastedge-plugin bash scripts/sync-reference-docs.sh
   ```

4. **Check for changes — exit early if none:**

   ```bash
   if git diff --quiet && git diff --cached --quiet; then
     echo "No doc changes — skipping release"
     exit 0
   fi
   ```

5. **Bump MCP server version to match plugin release:**

   ```bash
   # Use the plugin version from the dispatch payload to keep all three
   # consumers (Claude, Codex, MCP) on the same version number.
   if [ -n "$PLUGIN_VERSION" ]; then
     jq --arg v "$PLUGIN_VERSION" '.version = $v' package.json > tmp.json \
       && mv tmp.json package.json
   fi
   ```

6. **Commit to `main`, tag, and push:**

   ```bash
   git add reference-docs/ package.json
   git commit -m "release: v${PLUGIN_VERSION} — sync reference docs from fastedge-plugin"
   git tag -a "v${PLUGIN_VERSION}" -m "Release v${PLUGIN_VERSION} (synced from fastedge-plugin ${REF})"
   git push origin main --follow-tags
   ```

   The tag push triggers the existing `create-release.yaml` workflow, which builds and pushes the Docker image automatically.

**Notes:**

- Fully automated — no PR, no manual merge, no manual tagging. The dispatch from fastedge-plugin's release workflow triggers a complete sync → version bump → tag → Docker build pipeline.
- Sparse checkout avoids cloning the full fastedge-plugin repo (only reference dirs + index file).
- The workflow uses the plugin release tag, ensuring the MCP server syncs from a known-good versioned snapshot — not a moving `main` branch.
- Version lockstep: the MCP server's `package.json` version matches the fastedge-plugin release version, so all three consumers (Claude plugin, Codex plugin, MCP server) share the same version number.
- The existing `create-release.yaml` is triggered by the `v*` tag push — no changes needed to that workflow.
- Manual `workflow_dispatch` without a version payload skips the version bump (useful for testing sync without releasing).

**Test criteria:**

- [ ] `repository_dispatch` with `plugin-release` event triggers the workflow
- [ ] Manual dispatch with a specific tag/branch works
- [ ] `reference-docs/` files are updated on `main`
- [ ] `docs-index.local.json` is correctly generated (has `local_path` fields)
- [ ] `package.json` version matches the plugin release version
- [ ] Git tag `v{VERSION}` is created and pushed
- [ ] Tag push triggers `create-release.yaml` → Docker image is built
- [ ] If no docs changed, no commit/tag/release is created (idempotent)
- [ ] Full chain: fastedge-plugin release → dispatch → MCP sync → tag → Docker image (end-to-end)

### Task 6: Version bump utility

**Repo:** `fastedge-plugin`
**New file:** `scripts/bump-version.sh`

**Purpose:** Bumps the version field in both plugin manifests in lockstep.

**Behavior:**

```bash
# Usage: bump-version.sh [patch|minor|major]
# Reads current version from Claude plugin.json
# Bumps according to semver rules
# Writes new version to both plugin.json files
# Outputs new version to stdout
```

**Implementation notes:**

- Use `jq` for JSON manipulation (already available in GitHub Actions runners)
- Both plugins bump the same increment (patch/minor/major) and are set to the **same version number**
  - This ensures Claude plugin, Codex plugin, and MCP server all share one version
  - Pre-requisite: align both plugin manifests to `0.1.0` before first release run (Codex is currently `1.0.0`, needs to be set to `0.1.0`)
  - MCP server is currently `0.0.5` — the first release dispatch will set it to `0.1.0`
- The release workflow calls this script and captures the output version for the tag
- The MCP server's `package.json` version is set to this same version by Task 4's workflow
- First release produces `v0.1.0` across all three consumers, then weekly patches: `v0.1.1`, `v0.1.2`, etc.

**Test criteria:**

- [ ] `bump-version.sh patch` increments patch: `0.1.0` → `0.1.1`
- [ ] `bump-version.sh minor` increments minor and resets patch: `0.1.1` → `0.2.0`
- [ ] `bump-version.sh major` increments major and resets minor+patch: `0.2.0` → `1.0.0`
- [ ] Both `plugin.json` files are updated to the same version
- [ ] Pre-requisite: Codex plugin.json aligned from `1.0.0` to `0.1.0` before first run
- [ ] Script outputs the new version to stdout (for the release workflow to capture)
- [ ] Idempotent when run without committing (re-running reads the already-bumped value)

## What Users Experience Between Releases

| User type                                | Between releases                                                                                                                                                          | After release                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Claude/Codex plugin (on release tag)** | Using last release's docs — consistent and complete                                                                                                                       | `git pull` or marketplace update to get new version                        |
| **Claude/Codex plugin (on `main`)**      | `.md` files are current, `docs-index.json` is stale (gitignored). New topics won't appear in search. Existing topics work fine. Can run `generate-docs-index.sh` locally. | `git pull` picks up release commit with fresh index                        |
| **MCP server users**                     | Using Docker image from last release — consistent and complete                                                                                                            | New Docker image built automatically; `docker pull` or `--pull always`     |
| **Developers (internal)**                | Merge sync PRs freely, no conflicts. Run `generate-docs-index.sh` locally if needed.                                                                                      | Release workflow handles everything automatically — all 3 consumers update |

## Future: Marketplace Auto-Update (B3)

This plan builds the infrastructure for B3 without implementing it:

- **Versioned releases** with semver tags (`v0.1.1`, `v0.2.0`, etc.) are now created automatically
- **GitHub Releases** provide a stable API for version checking
- When Claude Code / Codex support marketplace auto-update:
  - Check installed plugin version against latest GitHub Release
  - Prompt user to update (or auto-update based on user preference)
  - The release tag ensures users always get a consistent snapshot (matching `.md` files + index)

No additional pipeline changes will be needed for B3 — only client-side update logic in the marketplace.

## Risks and Mitigations

| Risk                                                           | Likelihood                           | Mitigation                                                                                                                       |
| -------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| GitHub Actions cron skips a run                                | Low (rare at weekly intervals)       | Next scheduled run catches up. Manual dispatch available as override.                                                            |
| Cross-repo token expires or is revoked                         | Low                                  | Workflow step will fail visibly. Add a comment in workflow documenting which token/app to check.                                 |
| Developer on `main` has stale index                            | Medium (developers between releases) | Document in CLAUDE.md: "run `bash scripts/sync/generate-docs-index.sh` locally after pulling if you need fresh search results."  |
| Version bump conflicts if manual version change + cron overlap | Low                                  | Concurrency group prevents parallel runs. If a manual version bump happened, cron will read the new version and bump from there. |
| Multiple source repos release on the same day                  | Expected                             | This is the design's strength — sync PRs merge independently, release workflow batches them.                                     |
| MCP server auto-deploy introduces a bad Docker image           | Low                                  | MCP server only syncs reference docs — no code changes. If sync script has a bug, `create-release.yaml` build step will fail before pushing. Rollback: retag previous image as `latest`. |
