## Example-specific extraction hints

- This is a `.tsx` blueprint — the entry point is `src/index.tsx` and `tsconfig.json` must be included verbatim with JSX enabled
- The manifest ships 9 files; reproduce them verbatim in **Files to Create**, grouped by role:
  - **Edge handler source** — `src/index.tsx` (Hono app + three `createStaticServer` instances + JSX routes), `src/jsx-page.tsx` (the `<JsxContent />` page component using `hono/html` template literals + JSX layout)
  - **Generated asset modules, ship verbatim then noted as transient** — `src/styles-static-assets.ts`, `src/images-static-assets.ts`, `src/templates-static-assets.ts`. Preserve their `DO NOT EDIT — Generated by @gcoredev/FastEdge-sdk-js` banners. Note in **Build Notes** that `fastedge-assets` overwrites each of these on every build from its companion source directory
  - **Asset source directories (text)** — `styles/index.css`, `templates/index.html`. These are the durable user-owned content; ship the source example's content as a working starter
  - **Project config** — `package.json`, `tsconfig.json`
- **Dependencies to Add** (over `http-base`): runtime `"@gcoredev/fastedge-sdk-js": "^2.3.0"`, `"hono": "^4.11.9"`; dev `"npm-run-all2": "^8.0.4"`
- Preserve the full multi-step build pipeline in the `scripts` block:
  - `build`: `npm-run-all -s create-* build:wasm` (chains the three asset-manifest generators then builds the WASM)
  - `create-styles-manifest` / `create-images-manifest` / `create-templates-manifest`: each runs `npx fastedge-assets <source-dir> <target-ts-file>` to regenerate the asset manifest TypeScript module
  - `build:wasm`: `npx fastedge-build -i ./src/index.tsx -o ./dist/statics.wasm -t ./tsconfig.json`
- Extract the `createStaticServer` pattern: `import { createStaticServer } from "@gcoredev/fastedge-sdk-js"`, then three instances — one per asset class — each with its own `{ routePrefix }` option (`images`, `styles`) or no options (the templates server, which is read inline rather than mounted as a route)
- Show the two ways to consume a static server: `staticServer.serveRequest(c.req.raw)` (mount as an HTTP route, returning a `Response`) and `await staticServer.readFileString(path)` (read raw content, e.g. to inline into a JSX page)
- Preserve the Hono routing pattern: JSX page routes first (`/`, `/jsx`, `/template`), then catch-all glob routes for `/styles/*` and `/images/*` that delegate to `serveRequest`. Wire via `addEventListener('fetch', (event: FetchEvent) => event.respondWith(app.fetch(event.request)))`
- The `/jsx` route uses `c.html(<JsxContent {...props} />)` and demonstrates Hono's inline JSX → HTML rendering; the `<JsxContent />` component shows the `hono/html` template-literal `Layout` pattern alongside an inline JSX `Footer` to illustrate both rendering modes
- The `/template` route uses `templatesStaticServer.readFileString('/index.html')` then `c.html(templateString)` — show this as the recipe for serving inlined template strings vs. mounted static files
- **Build Notes — binary-asset gap**: the source example also has `images/gcore.png` and `images/home.png` (binaries). The plugin sync pipeline is markdown-oriented and does NOT ship those binary files. The scaffolded project will fail at `npm run create-images-manifest` unless the user populates `./images/` themselves. Surface this in **Build Notes** with two options: (1) drop user-supplied images into `./images/`, or (2) remove the `imagesStaticServer`, the `/images/*` route, and the `create-images-manifest` script if the user does not need image serving. Mirror the same caveat about emptying out the `<img src='/images/home.png' />` reference in `src/jsx-page.tsx`
- **Build Notes — generated modules**: the three `src/*-static-assets.ts` modules are NOT hand-written. They ship in the scaffold so `tsc` and editor TS servers succeed immediately, but they are overwritten by `fastedge-assets` on every `npm run build`. Tell the user to edit the asset source directories (`styles/`, `images/`, `templates/`), not the `*-static-assets.ts` files
- Cross-reference: the asset-manifest workflow is documented in detail in the assets-CLI reference and the static-sites guide
- "When to Use" hint: user wants to serve a small, build-time-bundled static site (HTML/CSS/images/templates) from a single FastEdge WASM with optional JSX-rendered pages and inline template composition — no external CDN, no separate origin
