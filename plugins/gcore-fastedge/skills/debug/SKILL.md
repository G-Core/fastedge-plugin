# /gcore-fastedge:debug

Generate a `fixtures/` directory containing scenario-specific debug configurations for the FastEdge visual debugger.

## What This Skill Does

The visual debugger (`npm run debug`) lets developers manually test their FastEdge app by loading
scenario configurations and inspecting request/response behaviour in a browser UI. This skill
generates those scenario configurations — each one a `.test.json` file that the debugger can load.

**This skill is independent of `/gcore-fastedge:test`.** Tests are CI assertions (pass/fail).
Fixtures are manual exploration scenarios. A developer may want one, both, or neither.

## Modes

The skill runs in one of two modes. Pick based on the user's intent — if unclear, ask.

| Mode | Trigger | Source of scenarios |
|---|---|---|
| **Manual** (default) | No flag, or `[project-dir]` only | The agent reads source code with developer collaboration and decides what scenarios matter — flexible, lower-volume, human-in-the-loop |
| **Inferred** | `--infer` flag | The agent applies the inference patterns in `reference/inference.md` to produce a structured scenario list automatically — repeatable, exhaustive on detected branches, no developer intervention |

Both modes produce the same fixture file format; only the **selection of scenarios** differs.

`--smoke-check` is an orthogonal flag (works with either mode). When set, after fixtures are written, the agent validates each one loads cleanly in the headless `@gcoredev/fastedge-test` runner. Catches syntactically valid but semantically broken fixtures (e.g. references to nonexistent env vars).

```
fixtures/                        ← Generated by this skill
├── happy-path.test.json         # Base case — simple successful request
├── germany.test.json            # Geo-routing: DE country code
├── missing-env.test.json        # Error case: required env var absent
├── .env                         # Test env vars and secrets
└── ...

tests/                           ← Generated by /gcore-fastedge:test (separate)
├── app.test.ts                  # CI assertions with defineTestSuite
└── ...
```

## Step 1 — Detect App Type

Determine whether this is an HTTP or CDN application:

| Signal | App Type |
|--------|----------|
| `Cargo.toml` with `proxy-wasm` dependency | CDN (proxy-wasm) |
| `asconfig.json` present | CDN (proxy-wasm, AssemblyScript) |
| `package.json` with `fastedge-build` in build script | HTTP (http-wasm) |
| `Cargo.toml` with `fastedge` or `wstd` dependency | HTTP (http-wasm) |

If ambiguous, ask the user.

---

## Step 2 — Identify Scenarios

The mechanic differs by mode.

### Manual Mode (default)

Read the app's entry point and identify features that need fixture coverage:

| Feature Detected | What to Generate |
|-----------------|-----------------|
| Geo-routing / country checks | One fixture per key country + a default/fallback fixture |
| KV Store access | Fixture with KV data note in description (KV is runtime, not configurable in fixture) |
| Environment variables (`getEnv`, `get_env`) | `.env` file with `FASTEDGE_VAR_ENV_*` prefixed test values |
| Secrets (`getSecret`, `get_secret`) | `.env` file with `FASTEDGE_VAR_SECRET_*` prefixed test values |
| Request path routing | One fixture per key route |
| Header inspection | Fixtures with different header combinations |
| Request body processing | Fixtures with body content |
| Authentication / JWT | Fixtures with valid and invalid auth headers |
| Error handling | Fixtures that trigger error paths |

**Always generate a `happy-path.test.json`** — the base case where everything works.

### Inferred Mode (`--infer`)

Read **`reference/inference.md`** and apply its patterns end-to-end to the project. Produce the inference output structure described in that file (hooks, env, secrets, properties, scenarios, testSeeds).

The output's `scenarios[]` array becomes the input to Step 3 — one fixture file per entry. Use the entry's `name`, `description`, `request`, and `properties` fields directly. Use the entry's `env` field (if present and differs between scenarios) to decide whether per-scenario .env subfolders are needed (see Step 3).

Do not deviate from the inference output unless you spot a quality-bar violation per `reference/inference.md` — in that case, reduce or expand and re-check before proceeding.

## Step 3 — Generate Fixtures

### Pre-flight: Existing `.test.json` Files

Before writing any fixture, scan `fixtures/` for existing `*.test.json` files. **Never silently overwrite** — hand-authored fixtures encode developer intent the skill cannot reconstruct from source alone. The canonical counterexample is a `missing-config.test.json` that deliberately omits the `dotenv` block to test the unset-env path; an inference-driven re-write would add `dotenv: { enabled: true, path: "." }` and silently invert the scenario.

Bucket each intended write against the existing state:

| Existing state for `<scenario>.test.json` | Action |
|---|---|
| File absent | Write fresh (no prompt). |
| File present, byte-for-byte match | Skip silently — already in sync. |
| File present, content differs | Hold for the prompt below. |

Existing fixtures with **no matching scenario in the inference output** are left untouched — they may be hand-authored cases the skill cannot derive (different request shapes, scenarios for features inference doesn't cover yet). Note them in the summary but do not prompt about them.

If any fixture lands in the "content differs" bucket, print a diff summary and prompt before writing:

```
Existing fixtures with content differing from --infer output:
  germany.test.json        — description differs
  missing-config.test.json — dotenv block differs (existing: omitted; inferred: enabled)
  us.test.json             — description differs

Existing fixtures with no matching scenario (will be left untouched):
  (none)

New scenarios to write (no existing file):
  happy-path.test.json
```

Use `AskUserQuestion` with three options (single-select; `[a]` first as the recommended default):

- **[a] Keep all existing fixtures, write only new scenarios** — preserves hand-authored content. Default.
- **[b] Replace all colliding fixtures with inferred drafts** — destroys hand-authored content; use only when intentionally regenerating.
- **[c] Cancel — exit without writing anything** — aborts the whole skill, including Step 4. Use when none of the offered actions match intent.

A "merge" option (keep existing fields, layer inferred fields on top) is deliberately not offered. The `missing-config` case shows why: existing fixture omits `dotenv` to test the unset-env path; a structural merge would add the `dotenv` block and break the scenario intent. Across all callers, merge is too risky.

### Pre-flight: `fixtures/.env`

If `fixtures/.env` already exists, **leave it untouched** and note its presence in the summary. Developers customize test env values — and may pair specific test secrets to local services; silently overwriting destroys that work. Print the existing file's content alongside what `--infer` would write so the developer can manually merge if they want.

If `fixtures/.env` does not exist, write the inferred file fresh (no prompt — nothing to clobber).

### After the pre-flight

Print a one-line summary of what changed:

```
Fixture pre-flight summary:
  Kept (existing preserved):    germany.test.json, missing-config.test.json, us.test.json
  Written (new scenarios):      happy-path.test.json
  Skipped (no inference match): (none)
  fixtures/.env:                preserved (existing) | written fresh
```

Then create the `fixtures/` directory if missing and write the fixtures the policy decided to write. Use the format sections below for each new or replaced fixture.

### CDN App Fixture Format (proxy-wasm)

```json
{
  "appType": "proxy-wasm",
  "description": "Human-readable scenario description",
  "request": {
    "method": "GET",
    "url": "http://fastedge-builtin.debug",
    "headers": {
      "host": "example.com"
    },
    "body": ""
  },
  "response": {
    "headers": {
      "content-type": "text/html"
    },
    "body": "<html>Mock origin response</html>"
  },
  "properties": {
    "request.country": "US",
    "request.host": "example.com",
    "request.path": "/test"
  },
  "dotenv": {
    "enabled": true,
    "path": "."
  },
  "logLevel": 2
}
```

**CDN-specific fields:**
- `request.url` — always use full URL (not `path`)
- `response` — mock origin response (what the CDN would fetch from origin)
- `properties` — CDN properties the filter can read (`request.country`, `request.host`, `request.path`, `client.ip`, etc.)

### HTTP App Fixture Format (http-wasm)

```json
{
  "appType": "http-wasm",
  "description": "Human-readable scenario description",
  "request": {
    "method": "GET",
    "path": "/api/data",
    "headers": {
      "geoip-country-code": "FR"
    }
  },
  "dotenv": {
    "enabled": true,
    "path": "."
  }
}
```

**HTTP-specific fields:**
- `request.path` — path only (not full URL)
- No `response` field (HTTP apps generate their own response)
- No `properties` field (geo data comes via request headers like `geoip-country-code`)

### Fixture .env File

If the app uses environment variables or secrets, generate `fixtures/.env`:

```bash
# Environment variables
FASTEDGE_VAR_ENV_BASE_URL=https://api.example.com
FASTEDGE_VAR_ENV_DEBUG=true

# Secrets (test values only — never use real credentials)
FASTEDGE_VAR_SECRET_API_KEY=test-api-key-12345
FASTEDGE_VAR_SECRET_DB_PASSWORD=test-password
```

Set `dotenv.enabled: true` and `dotenv.path: "."` in each fixture to load from the fixtures directory.

### Per-Scenario .env (Inferred Mode Only)

When inference detects that env values **must differ** between scenarios (e.g. `EXPERIMENT_NAME=A` for variant-a, `EXPERIMENT_NAME=B` for variant-b), put each scenario's overrides in a subfolder:

```
fixtures/
├── .env                              # Shared defaults
├── variant-a.test.json               # dotenv.path: "./variant-a"
├── variant-a/.env                    # FASTEDGE_VAR_ENV_EXPERIMENT_NAME=A
├── variant-b.test.json               # dotenv.path: "./variant-b"
└── variant-b/.env                    # FASTEDGE_VAR_ENV_EXPERIMENT_NAME=B
```

Each per-scenario `.env` is **additive** to the shared `fixtures/.env` — only include vars that override defaults. Do not duplicate shared values.

Manual mode rarely needs this — keep things simple with a single shared `.env` unless the developer asks for divergent values.

## Step 4 — Add Debug Script

### Pre-flight: Governance Detection

Before touching `package.json`, decide whether the project's governance allows the skill to modify tracked files. Resolve the policy in this order:

1. If `--no-modify-project` was passed → **off** (skip mutation; print recommendations only).
2. If `--modify-project` was passed → **on** (mutate, overriding any auto-detect signal).
3. Auto-detect: walk up from `<project-root>` toward the filesystem root, reading `AGENTS.md` and `CLAUDE.md` at each directory level. Stop the walk at the **git repository root** when it can be determined (`git -C <project-root> rev-parse --show-toplevel`); if `<project-root>` is not inside a git repo, stop at `/`. Case-insensitively substring-match each file's contents for `"never change code"` (catches "never change code that was not asked to change" and equivalent variants). If any encountered file matches → **off** (and remember the path that matched, for use in the policy message below). If no match is found along the entire walk → **on**.

   Rationale: nested example layouts (e.g. `<sdk-repo>/examples/<example>/`) typically have no `AGENTS.md` of their own — the governance rule lives at the SDK repo root one or more levels up. A strict project-root-only check would silently bypass the protection in these cases.

**Surface the resolved policy verbosely** so the user understands what's happening and how to override:

When auto-detected **off** (governance signal found):
```
Detected "never change code" rule in <path-relative-to-project-root>.
Skipping package.json mutation — printing recommended commands instead.
Pass --modify-project to override.
```

Render `<path-relative-to-project-root>` as the matching file expressed relative to the project-root — e.g. `AGENTS.md` when the rule is at project-root, `../AGENTS.md` when it's one level up, `../../CLAUDE.md` when two levels up, etc. This makes the policy decision auditable: the user can see exactly which file triggered the off resolution.

When auto-detected **on** (no governance signal anywhere on the walk):
```
No "never change code" rule detected in any AGENTS.md / CLAUDE.md from
<project-root> up to <walk-stop-path>. Will add "debug" script to
package.json if missing. Pass --no-modify-project to skip.
```

Render `<walk-stop-path>` as either the git repo root or `/`, whichever ended the walk. Showing the bound makes it clear how far the auto-detect actually looked.

When explicit `--no-modify-project`:
```
--no-modify-project: skipping package.json mutation; printing
recommendations below.
```

When explicit `--modify-project`:
```
--modify-project: mutating package.json as needed (overriding any
governance auto-detect).
```

### Policy: ON — Mutate

Behavior branches on host language (Cargo.toml without root package.json → Rust; otherwise JS/TS / AS).

**Rust** — write the script into `fastedge-test/package.json` (creating the sandbox if absent):

```json
{
  "scripts": {
    "debug": "npx @gcoredev/fastedge-test --project-dir .."
  }
}
```

If `fastedge-test/` does not exist yet, tell the user that running `/gcore-fastedge:test` first will set it up; do not silently scaffold the sandbox from this skill.

Verify `@gcoredev/fastedge-test` is in `fastedge-test/package.json` devDependencies. If missing, recommend (do not install automatically):
```bash
cd fastedge-test && npm install --save-dev @gcoredev/fastedge-test@latest
```

**JS/TS / AssemblyScript** — write the script into the root `package.json`:

```json
{
  "scripts": {
    "debug": "npx @gcoredev/fastedge-test"
  }
}
```

Verify `@gcoredev/fastedge-test` is in root devDependencies. If missing, recommend:
```bash
npm install --save-dev @gcoredev/fastedge-test@latest
```

For Rust, the `--project-dir ..` flag anchors the debugger on the project root (where `fastedge-config.test.json` and `fixtures/` live) when the script runs from inside `fastedge-test/`. Requires `@gcoredev/fastedge-test` 0.2.3+.

### Policy: OFF — Recommend

Do **not** modify any `package.json`. Instead, print the actions the developer can take manually if they want the visual debugger wired up.

**Rust:**

```
To enable the visual debugger for this Rust app, run:

  mkdir -p fastedge-test
  cd fastedge-test
  npm init -y
  npm install --save-dev @gcoredev/fastedge-test@latest

Then add this entry to fastedge-test/package.json's "scripts" block:

  "debug": "npx @gcoredev/fastedge-test --project-dir .."

Run the debugger with:

  cd fastedge-test && npm run debug

(Or use the VSCode extension — "FastEdge: Debug Application" — which bundles
its own server and doesn't need this setup.)
```

**JS/TS / AssemblyScript:**

```
To enable the visual debugger in this project, run:

  npm install --save-dev @gcoredev/fastedge-test@latest

Then add this entry to package.json's "scripts" block:

  "debug": "npx @gcoredev/fastedge-test"

Run the debugger with:

  npm run debug
```

In all cases, append the footer:

```
(The skill skipped these because the project's governance rules disallow
changes the user did not explicitly request. The generated fixtures in
fixtures/ are unaffected — those are this skill's product, not source
modifications.)
```

This applies whether the policy was set off explicitly (`--no-modify-project`) or auto-detected. The fixture generation in Step 3 proceeds regardless — Step 4's governance only gates `package.json` mutation.

## Step 5 — Smoke Check (Optional, `--smoke-check` only)

Skip this step unless `--smoke-check` was passed.

For each generated `.test.json`, run a non-asserting load via the headless test runner to confirm the fixture parses and the WASM executes without immediate error. Command depends on host language:

**Rust** (the runner is installed in `fastedge-test/node_modules/`):
```bash
cd fastedge-test
npx @gcoredev/fastedge-test --project-dir .. ../fixtures/<scenario>.test.json --no-assert
```

`--project-dir ..` makes the debugger resolve config/fixtures relative to the project root. The fixture path is `../fixtures/...` because CWD is `fastedge-test/`.

**JS/TS / AssemblyScript** (runner in root `node_modules/`):
```bash
npx @gcoredev/fastedge-test ./fixtures/<scenario>.test.json --no-assert
```

(If the runner version installed in the project doesn't support `--no-assert`, fall back to running the fixture inside a minimal `defineTestSuite` wrapper that asserts only "did not throw".)

Report the result for each fixture: PASS (loaded cleanly), FAIL (parse error, runtime error, or fixture references nonexistent env var). On FAIL, surface the error and offer to regenerate that scenario.

The smoke check verifies fixture **well-formedness only** — not behavioral correctness. Behavioral assertions belong in `/gcore-fastedge:test` (CI) and `/gcore-fastedge:live-test` (deployed verification).

## Step 5.5 — Rust Stderr Logging Pre-Check (Rust projects only)

**Skip this step entirely for TypeScript, JavaScript, and AssemblyScript projects.** Both `@gcoredev/fastedge-sdk-js` (via `console-override.cpp`) and `@gcoredev/proxy-wasm-sdk-as` (via `runtime.ts`'s `process.stdout.write`) route every logging call through stdout. There is nothing to check.

**For Rust projects only** (`Cargo.toml` present at `<project-root>`), run a static scan **before** printing usage so the developer is warned about a known foot-gun before they open the visual debugger and waste time wondering why expected log lines never appear.

The visual debugger surfaces the WASM module's stdout in its log pane. Stderr is silently dropped — exactly the symptom a developer would mistake for "my hook isn't being called" or "my fixture is wrong." This pre-check exists to short-circuit that confusion.

### Procedure

1. Glob all `.rs` files under `<project>/src/`.
2. Grep each file for the following stderr-bound patterns:
   - `\beprintln!` — stderr macro
   - `\beprint!` — stderr macro
   - `std::io::stderr\s*\(\s*\)` / `io::stderr\s*\(\s*\)` — direct stderr handle
   - `env_logger::(init|Builder::new)` not followed by `Target::Stdout` — env_logger defaults to stderr
   - `with_writer\s*\(\s*std::io::stderr` — tracing-subscriber stderr override
   - `proxy_wasm::hostcalls::log\s*\(` / `hostcalls::log\s*\(` — proxy-wasm log hostcall; FastEdge does not capture hostcall-level logs (stdout only); use `println!()` instead
3. Collect every hit as `(file, line, matched_token, full_line_text)`.

### When matches are found

Print this warning **before** the Step 6 "Print Usage" output, so the developer sees it first in the terminal:

```
⚠ Stderr-bound logging detected — debugger log pane will be empty for these calls.

  <file>:<line>  <matched_token>
      <full_line_text>
  [...repeat per hit, up to 5; if more, append "(+N additional matches)"]

  FastEdge captures stdout only. The visual debugger's log pane reads stdout —
  anything written to stderr is silently dropped, producing the false impression
  that the hook didn't run, the fixture is wrong, or logging is broken.

  Fix before debugging: convert to println!/print! (all Rust apps — HTTP and
    CDN). Direct stderr writers, env_logger defaults, tracing-subscriber
    stderr overrides, and proxy_wasm::hostcalls::log calls each need manual
    review — see plugins/gcore-fastedge/CLAUDE.md § "Logging — Stdout Only
    (Rust Hazard)".
```

Do **not** auto-rewrite the source from this skill — the developer's project is their own; the scaffold skill's Step 4e self-check is the auto-rewrite layer, and that only fires on freshly-scaffolded code where the agent itself authored the bug. By the time `/gcore-fastedge:debug` runs, the source belongs to the user and they need to choose what to do with it.

### When no matches are found

Proceed silently to Step 6. No success message is printed — the absence of a warning is the signal.

## Fixture Naming Convention

Use descriptive kebab-case names that describe the scenario:

- `happy-path.test.json` — always present, base success case
- `germany.test.json` — geo-routing: country DE
- `auth-valid-token.test.json` — authentication: valid JWT
- `auth-expired-token.test.json` — authentication: expired JWT
- `cache-miss.test.json` — KV store: key not found
- `missing-env.test.json` — error: required env var not set
- `post-json-body.test.json` — POST request with JSON body
- `404-not-found.test.json` — error page scenario

The `.test.json` suffix is required — the debugger recognises this extension.

## Examples by App Type

### Geo-Redirect CDN App

```
fixtures/
├── .env                    # FASTEDGE_VAR_ENV_DEFAULT, FASTEDGE_VAR_ENV_DE, FASTEDGE_VAR_ENV_US
├── happy-path.test.json    # US user → redirects to US origin
├── germany.test.json       # DE user → redirects to DE origin
├── default.test.json       # FR user (unmapped) → falls back to default origin
└── no-country.test.json    # Missing country property → default behaviour
```

### API Proxy HTTP App

```
fixtures/
├── .env                    # FASTEDGE_VAR_ENV_API_URL, FASTEDGE_VAR_SECRET_API_KEY
├── happy-path.test.json    # GET /api/data → 200
├── post-create.test.json   # POST /api/items with JSON body
├── auth-missing.test.json  # GET /api/data without auth header → 401
└── not-found.test.json     # GET /unknown-route → 404
```

### JWT Auth CDN App

```
fixtures/
├── .env                    # FASTEDGE_VAR_SECRET_JWT_SECRET
├── happy-path.test.json    # Valid JWT in Authorization header → passes through
├── auth-expired.test.json  # Expired JWT → 401
├── auth-missing.test.json  # No Authorization header → 401
└── auth-malformed.test.json # Malformed token → 400
```
